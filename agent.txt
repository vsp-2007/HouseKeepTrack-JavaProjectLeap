1. Architecture Overview:
   - Framework: Spring Boot 3.x (with Java 25 LTS) using Spring Web, Spring Data JPA, Bean Validation, MySQL Connector.
   - Layered Design:
     * Controller Layer: REST endpoints with explicit DTOs and validation (@Valid, @NotNull, etc.).
     * Service Layer: Enforces strict lifecycle state machine and business invariants before DB operations.
     * Repository Layer: Spring Data JPA interfaces for Room, Housekeeper, CleaningTask, Inspection.
     * Exception Handling: @RestControllerAdvice handling CustomBusinessRuleException, ResourceNotFoundException, and MethodArgumentNotValidException.
   - Core Entities & Relations:
     * Room (1) -> (M) CleaningTask
     * Room (1) -> (M) Inspection
     * Housekeeper (1) -> (M) CleaningTask
     * Room: id, roomNumber, roomType, status [DIRTY, IN_CLEANING, CLEANED, INSPECTED, READY, OCCUPIED], activeCleaningTaskId, dirtyAt, readyAt.
     * Housekeeper: id, name, email, phone, status [AVAILABLE, BUSY, OFFLINE], activeTaskCount.
     * CleaningTask: id, room_id, housekeeper_id, status [PENDING, IN_PROGRESS, COMPLETED, CANCELLED], priority [HIGH, NORMAL], assignedAt, startedAt, completedAt, notes.
     * Inspection: id, room_id, supervisorName, result [PASSED, FAILED], failureReason, inspectedAt.

2. Contradictions & Ambiguities Resolved (User Feedback Incorporated):
   - Dual-Path Inspection Lifecycle & Priority Re-cleaning:
     * Room lifecycle: DIRTY -> IN_CLEANING -> CLEANED -> INSPECTED -> (READY or DIRTY).
     * When a supervisor inspects a CLEANED room, it transitions to INSPECTED with the recorded inspection result.
     * From INSPECTED, there are two distinct paths:
       a) Path 1 (PASSED): Supervisor can transition room to READY (markReady endpoint). Only rooms with PASSED inspection can be marked READY.
       b) Path 2 (FAILED / Re-cleaning needed): Due to improper works or failed inspection, supervisor sends the room back to cleaning. Room status transitions back to DIRTY, and a new HIGH-PRIORITY CleaningTask is auto-generated with failure notes and auto-assigned.
     * Crucially: INSPECTED is a necessary intermediate stage; markReady is not the only path for INSPECTED.
   - Priority-based Auto-assignment Queuing:
     * When a housekeeper completes a task or becomes available, the system assigns the highest-priority pending task first.
     * Two sources of High Priority:
       1) Inspection-failed rooms: assigned HIGH priority immediately to rectify defects quickly.
       2) Longest-wait rooms: pending tasks are dynamically escalated to HIGH priority or ordered by longest wait time (oldest dirtyAt/assignedAt), ensuring rooms that have waited the longest are prioritized and never starved.
     * Dispatch Order: HIGH priority tasks (failed rooms + longest-waiting escalated rooms) dispatched first, ordered by oldest wait time (FIFO within priority band).
   - Turnaround Time:
     * Track both cleaning turnaround time per housekeeper (startedAt to completedAt) and total room turnaround time (dirtyAt to readyAt).

3. Important Points & Business Rules:
   - Priority Dispatch Invariant: Both inspection-failed rooms and longest-waiting rooms receive high priority in the assignment queue to minimize room downtime and turnaround latency.
   - Service Layer Invariant: A room cannot be allocated/checked-in to a guest unless status is strictly READY.
   - Forward-only Lifecycle with Re-cleaning Loop: Transitions strictly follow the lifecycle. The only permitted regression is from INSPECTED/CLEANED -> DIRTY when inspection fails or re-cleaning is required.
   - Immediate Validation: Invalid transitions must reject requests with HTTP 400 Bad Request / 409 Conflict with descriptive error payloads instead of stack traces or DB errors.
   - MySQL Auth: Verified and confirmed with root / v2i0s0n7u on MySQL80 service. Database: housekeeptrack_db.
   - Code Quality & Modularity: Clean modular components, explicit DTOs, idempotent actions where applicable, short and clear comments explaining state machine and queue logic.

   - Model Layer:
     * Domain Entities: Room, Housekeeper, CleaningTask, Inspection mapped via Spring Data JPA / Hibernate.
     * Repositories: RoomRepository, HousekeeperRepository, CleaningTaskRepository, InspectionRepository.
     * Business Services: RoomService, HousekeeperService, CleaningTaskService, InspectionService, MetricsService enforcing domain state machine rules, transactional boundaries, and invariants.

   - View Layer (RESTful JSON Views & DTOs):
     * Request DTOs: CreateRoomRequest, CreateHousekeeperRequest, CreateInspectionRequest, UpdateHousekeeperStatusRequest.

   - Controller Layer (Spring MVC REST Controllers):
     * Spring MVC REST controllers (@RestController) handling HTTP routing, request validation, and mapping model responses:
       RoomController, HousekeeperController, CleaningTaskController, InspectionController, MetricsController.
     * Global Exception Advice: @RestControllerAdvice handling exceptions centrally and returning structured JSON error views.

2. Enforced Business Rules & Invariants:
   - Check-in Allocation Barrier: Room cannot transition to OCCUPIED unless status is strictly READY. Invalid attempts throw InvalidRoomStateException returning HTTP 400 with clean error message.
   - Dual-Path Inspection from CLEANED and INSPECTED:
     * PASSED: Room transitions to INSPECTED, becoming eligible for READY status.
     * FAILED / Defect Found: Room status reverts to DIRTY, auto-generates a HIGH-priority re-cleaning task with supervisor failure notes, and auto-dispatches.
     * Crucially: INSPECTED status supports both markReady (Path 1) and send-to-cleaning / failed re-inspection (Path 2) without blocking defects found during final checks.
   - Mark Ready Invariant: Room must be in INSPECTED status and have passed inspection before moving to READY.

3. Priority Queue, Dynamic Escalation & Auto-Dispatch:
   - Priority bands: HIGH before NORMAL, then oldest FIFO by assignedAt / createdAt (COALESCE(t.assignedAt, t.createdAt) ASC).
   - Dynamic escalation: Long-waiting PENDING tasks escalate to HIGH priority after threshold (based on both task creation time and room dirtyAt).
   - Auto-assignment occurs reactively whenever a task is created, a housekeeper is registered, housekeeper status changes to AVAILABLE, or a task is completed.
   - Staff Availability Protection: Setting a housekeeper to OFFLINE re-queues active tasks to PENDING, resets room to DIRTY, and immediately dispatches to other available staff so rooms are never stranded. Guard prevents setting BUSY staff to AVAILABLE. Task completion preserves OFFLINE status for clocked-out staff.

4. Metrics & Exception Handling:
